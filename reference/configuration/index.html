    Configuration Reference¶

    Most package behavior is controlled through configuration. Configuration tells matchminer-ai which models to use, whether LLM calls should run locally or through a remote endpoint, where to cache model metadata, and how individual workflow steps should be run.

    Most users can start with the built-in default settings. You usually only need to change configuration when you want to change models, switch between local and remote inference, adjust runtime settings, enable debug output, or point the package at a different endpoint.

    Use load_default_preset() when you want to start from the package defaults and change a few values in Python:

    from matchminer_ai import load_default_preset

config = load_default_preset()
config.remote["enabled"] = True
config.remote["server_urls"] = ["http://localhost:8000/v1"]

    Custom Config Files¶

    The optional guideline extractor uses config.guideline with the same task-level remote.model_name, remote.request_params, and remote.extra_body structure. It requires shared remote mode and writes to an explicit external output directory. See guideline extraction for context, output reserve, reasoning, concurrency, and source-provenance settings. Existing custom YAML files without a guideline section continue to load; copy that section from the default preset before using this optional API.

    For package installs, treat the built-in preset files as read-only package data. For larger or reusable changes, copy the default preset values into a YAML file in your project, edit them, and load that file by path:

    from matchminer_ai import load_config

config = load_config("my_config.yaml")

    Root Keys¶

    debug_mode¶

    Boolean flag used by summarization postprocessing. When true, selected intermediate columns are retained in output tables.

    model_metadata_cache_dir¶

    Directory path used by model metadata helpers to cache Hugging Face model metadata JSON files.

    Returned Metadata¶

    Functions with return_metadata=True return the package version, resolved configuration snapshot, and model provenance collected by the package. Model metadata is keyed by the public operation that used the model:

    {
  "model_metadata": {
    "summarize_patients": {
      "model_name": "organization/model",
      "model_sha": "..."
    }
  }
}

    For HTTP inference, the entry describes the requested remote.model_name looked up on Hugging Face. When that name is not a Hub model ID, model_sha is openai-compatible-endpoint and metadata_error records the lookup failure. Where the server reports per-response provenance, it is listed under responses. Neither verifies the weights the endpoint actually serves.

    Payloads written before 0.6 used role keys such as embedding_model and match_quality_checker. Readers of saved embedding metadata still accept embedding_model.

    remote¶

    Global transport settings used when remote.enabled is true and LLM tasks send OpenAI-compatible chat completion requests to external endpoints. The default tested setup is a vLLM server with a compatible reasoning parser. Task-specific request payload settings live under each task's remote block. The remote backend reads the API key from the OPENAI_API_KEY environment variable. API keys are not stored in preset files.

    Google Agent Platform (Gemini and MaaS) is supported through its OpenAI-compatible Chat Completions route. Set remote.provider to google_agent_platform; the package then uses Google Application Default Credentials (ADC), refreshes the OAuth access token for each request, converts a leading system message to the user-first form required by managed open models, and omits vLLM-only extra_body values. Install-time dependencies include google-auth; credential files and tokens are never stored in package configuration.

    remote.enabled¶

    Selects the remote LLM backend when true.

    remote.provider¶

    Authentication and message-compatibility profile. openai is the default and reads OPENAI_API_KEY. google_agent_platform uses ADC and ignores OPENAI_API_KEY. databricks_anthropic sends structured requests to Claude through a Databricks AI Gateway's Anthropic Messages route, authenticated with a Databricks profile (databricks_profile). Only structured requests support it, such as the SQL workup agent; see SQL-agent workup checks.

    For example, Gemma 4 26B A4B IT MaaS in a project named my-gcp-project uses:

    config.remote.update(
    {
        "enabled": True,
        "provider": "google_agent_platform",
        "google_project_id": "my-gcp-project",
        "server_urls": [
            "https://aiplatform.googleapis.com/v1/projects/my-gcp-project/"
            "locations/global/endpoints/openapi"
        ],
    }
)
for task in (
    config.trial,
    config.patient,
    config.llm_match_quality,
    config.llm_exclusion_criteria,
    config.llm_good_option,
):
    task["remote"]["model_name"] = "google/gemma-4-26b-a4b-it-maas"

    Set up ADC through the runtime environment, an attached service account, or gcloud auth application-default login. The selected endpoint must still be authorized for the sensitivity of any clinical text sent to it.

    check_openai_endpoint() uses a minimal patient-free chat completion for this provider because the MaaS OpenAI route does not document /models.

    Gemini 3.8 Flash uses the same global endpoint and ADC profile with model google/gemini-3.8-flash. System messages are retained for Gemini. Its supported reasoning efforts are low, medium, and high; the provider maps an xhigh request to high. Explicit sampling fields and vLLM extensions are omitted, because Gemini 3.8 manages sampling internally.

    For patient summarization and review_patient_workup, configure the patient task after setting the Google remote profile above:

    config.patient.update(
    sampling_profile="none", reasoning_effort="high",
    context_window=1048576, tokenizer_mode="bytes",
)
config.patient["local"]["engine"]["max_model_len"] = 1048576
config.patient["local"]["chat_template_kwargs"] = {}
config.patient["remote"].update(
    model_name="google/gemini-3.8-flash",
    tokenizer_name="Qwen/Qwen3-0.6B",
    request_params={"max_tokens": 65536, "reasoning_effort": "high"},
    extra_body={},
)

    The local tokenizer supplies chunk boundaries only; byte accounting conservatively bounds the hosted-model prompt instead of claiming exact Gemini token counts. Workup review skips vLLM discovery/tokenization routes, refreshes ADC for structured requests, and retains its normal JSON schema and exact patient-note quote validation. These settings do not change a separately configured guideline catalog run.

    remote.google_project_id¶

    Optional Google Cloud quota project supplied when remote.provider is google_agent_platform. The endpoint URL still determines the project that receives the inference request.

    remote.server_urls¶

    List of OpenAI-compatible base URLs. Values are passed to the OpenAI client as base_url. For the default Nemotron 3.5 Super configuration, the server should be a vLLM chat endpoint launched with the nemotron_v3 reasoning parser, the qwen3_coder tool-call parser and --trust-remote-code; the package start_vllm_servers() helper adds these flags from the selected LLM task's reasoning_parser, tool_call_parser and local engine settings.

    Model names and request parameters are configured per LLM task under that task's backend block. For example, trial.local.model_name is the model loaded by local vLLM, trial.remote.model_name is the model string sent to the endpoint, trial.remote.request_params contains top-level chat completion request fields, and trial.remote.extra_body contains fields sent through request extra_body.

    Remote mode expects the endpoint to return final answer text in message.content. The default vLLM/Nemotron setup can expose reasoning separately via vLLM reasoning parser support. Other OpenAI-compatible endpoints may work only if they return final answer text in message.content; endpoints that include reasoning text in message.content are not currently supported.

    remote.max_concurrent_requests¶

    Maximum number of concurrent requests per remote server; default 32. Guideline clients in one Python process share this cap across diseases for the same endpoint. Independent processes have separate caps, so use the collection runner rather than launching multiple independent 32-request processes.

    remote.request_timeout¶

    Request timeout in seconds.

    remote.max_retries¶

    Maximum retry attempts for a failed remote request. The package disables the OpenAI SDK's separate internal retry loop so this setting is the single retry bound.

    remote.batch_size¶

    Number of prompts processed per remote-server batch.

    remote.retry_backoff_base¶

    Base value, in seconds, for exponential retry backoff.

    Model-aware sampling and reasoning¶

    The default preset sets sampling_profile: auto and reasoning_effort: xhigh on every LLM stage: trial, patient, llm_match_quality, llm_exclusion_criteria, and guideline. The selected model determines defaults for both in-process vLLM and OpenAI-compatible vLLM requests. Quantized model IDs containing the same family name are recognized. Guideline discovery applies the profile after /v1/models identifies the actual served model.

    Model / mode Temperature Top-p Top-k Other sampling defaults
    Nemotron 3.5 Super (default) 1.0 0.95 Disabled (-1) min-p 0, presence penalty 0, repetition penalty 1
    Gemma 4 1.0 0.95 64 Engine defaults for penalties
    Qwen 3.8, thinking 1.0 0.95 20 min-p 0, presence penalty 0, repetition penalty 1
    Qwen 3.8, non-thinking 0.7 0.8 20 min-p 0, presence penalty 1.5, repetition penalty 1
    Reflection Beam 1.0 0.7 0.99 Disabled (-1) min-p 0, presence penalty 0, repetition penalty 1

    Nemotron's temperature and top-p follow NVIDIA's model card (checked 2026-10-15); its other sampling controls are neutral. The others follow the vendor recommendations checked on 2026-09-24: Google Gemma 4, Qwen3.8-Flash-Next, and Qwen3.8-27B. Beam's temperature, top-p, and repetition penalty follow its generation configuration, verified on 2026-10-16; its other sampling controls are neutral. Official Beam 1.0 IDs, quantized variants, and the short aliases beam and reflection-beam are recognized. Local server startup selects beam for both reasoning and tool parsing and requires a Beam-compatible vLLM build. Beam always reasons. The workspace defaults chat_template_kwargs.reasoning_effort to medium rather than the upstream template's max, without inferring an enable_thinking switch. Explicit template or API effort overrides and output budgets are retained. When both API and template effort are supplied, they must agree.

    Qwen defaults to thinking enabled, preserved thinking, and xhigh effort. Supported effort values are xhigh, medium, and low. Remote requests send reasoning_effort at the API level and in chat_template_kwargs; local prompt rendering and endpoint token counting use the same template setting. Gemma 4 supports thinking enabled/disabled, not graded reasoning effort: its profile sets enable_thinking: true and does not invent an xhigh control.

    Explicit local.generation, local.chat_template_kwargs, remote.request_params, and remote.extra_body values override profile defaults. To turn thinking off, set the applicable chat_template_kwargs.enable_thinking to false. The Qwen profile then selects the non-thinking sampling defaults. Set a stage's sampling_profile to none to use entirely explicit settings; gemma4, qwen3.8, and reflection-beam (or beam) also allow explicit family selection for endpoint aliases. Unknown model families receive no automatic vendor settings. Existing custom configs without sampling_profile keep their explicit behavior, with one exception: a section without sampling_profile served by Nemotron 3.5 Super (any ...nemotron-3.5-super-vl... model name, profile replaces_task_sampling; user instruction 2026-11-05) sends NVIDIA's sampling (temperature 1.0, top_p 0.95, top_k -1, min_p 0, repetition_penalty 1.0) in place of its fixed values, on the local and remote paths, keeping an explicit thinking switch. Name a profile (explicit keys then win) or set sampling_profile: none to keep a section's own sampling for Nemotron.

    This intentionally replaces the earlier preset's greedy patient/checker LLM sampling and mismatched Gemma top-k. Matching model versions, output budgets, and clinical prompts are unchanged. Existing generated artifacts retain their original settings; changed extraction settings require a fresh run directory.

    config = load_default_preset()
config.remote["enabled"] = True
config.remote["server_urls"] = ["http://your-server:8001/v1"]
config.remote["max_concurrent_requests"] = 32
config.trial["remote"]["model_name"] = "Qwen/Qwen3.8-Flash-Next"
# For patient summarization, update both model_name and tokenizer_name.
# Optional explicit override:
config.trial["remote"]["request_params"]["reasoning_effort"] = "medium"

    Model-specific reasoning text: the literal Reasoning: high system header is added only for GPT-OSS model identities. Gemma, Nemotron, Qwen, and other families use their configured chat-template/API thinking controls; task instructions are preserved without the GPT-OSS header. Unknown model identities receive no header.

    trial¶

    Task configuration for trial summarization.

    trial.local¶

    Local in-process vLLM runtime settings:

    • model_name: model identifier loaded by local vLLM and used for local tokenizer/chat-template rendering and model metadata lookup.
    • engine: keyword arguments passed to vllm.LLM(...); the package passes model=trial.local.model_name separately. Every default engine serves Nemotron 3.5 Super as the production servers do: trust_remote_code, language_model_only, enable_prefix_caching, mamba_backend: flashinfer, mamba_ssm_cache_dtype: float16, enable_mamba_cache_stochastic_rounding, mamba_cache_philox_rounds: 5 and mamba_cache_mode: align, with tensor_parallel_size: 1 (the NVFP4 build needs a Blackwell GPU). The vLLM server helpers pass these keys as the same vllm serve flags.
    • generation: keyword arguments passed to vllm.SamplingParams(...).
    • chat_template_kwargs: keyword arguments passed to tokenizer chat-template rendering.

    Additional engine and generation keys may be included if they are valid vLLM keyword arguments. vLLM validates those keys when the engine/request is created.

    trial.prompt_files¶

    Prompt template filenames loaded from matchminer_ai.prompts for the legacy one_shot method (primer, question).

    trial.cohorts¶

    Settings of the default cohorts method, the three-step workflow shared with protocol_cohort_extraction: max_attempts (per request, 1-10, default 3), structured_outputs (default true; each remote request is constrained by its step's JSON schema), chunk_size (default 500) and chunks_in_flight (default 2, at most 16), and optional prompt_files mapping screen, list and criteria to other packaged prompt files. A remote backend keeps chunk_size * chunks_in_flight requests in flight, sending each on its own as another returns, so one slow answer holds up only itself; a local backend gets batches of chunk_size requests of one step, chunks_in_flight at once. The merge and boilerplate steps (merge_equivalent_cohorts, remove_boilerplate_criteria) and screen_trials use the same settings.

    trial.reasoning_parser¶

    vLLM reasoning parser name. The default auto resolves known model names, including the default nvidia/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B-NVFP4 to nemotron_v3 and google/gemma-4-31B-it to gemma4. Set this explicitly when using a model not covered by the package mapping, or use none to disable reasoning parsing for a non-reasoning model. This setting applies to local vLLM execution and vLLM server launch helpers; non-vLLM remote endpoints may ignore it or return no separate reasoning field.

    trial.remote¶

    Task-specific remote chat completion request settings:

    • model_name: model name sent in OpenAI-compatible chat completion requests and used for remote endpoint metadata.
    • request_params: top-level chat completion request fields sent as-is, including the output-token budget. Use max_tokens for vLLM and many compatible endpoints, or max_completion_tokens for endpoints that require it.
    • extra_body: provider-specific fields sent as request extra_body when non-empty.

    The package interprets model_name and fills missing values from the selected sampling profile. Explicit values inside request_params and extra_body otherwise pass through; the Qwen profile validates its supported reasoning levels. The OpenAI client or remote endpoint validates other API fields.

    trial.boilerplate_marker¶

    Line marker used by trial postprocessing to identify the boilerplate exclusion section heading.

    patient¶

    Task configuration for patient summarization.

    patient.chunk_size¶

    Maximum character count used when splitting patient notes into serial summary chunks.

    patient.chunk_overlap¶

    Character overlap between adjacent patient-note chunks.

    patient.prompt_margin_tokens¶

    Token margin reserved when truncating patient chunks before prompt rendering.

    patient.scheduling¶

    How serial summarization shares the backend among patients: continuous (default) or rounds. Each patient's chunks are always summarized in order, each prompt carrying the summary accepted for the previous chunk.

    • continuous: with a remote backend, each patient's next chunk is sent as soon as the previous one is final, after its quality retries. Up to the endpoints' request capacity is in flight: each listed server's remote.max_concurrent_requests, or with an endpoint pool the sum of its registry's per-server ceilings (upstream_concurrency), reread while it runs; an adaptive pool's requests above its current limits wait for its slots. Waiting patients start longest remaining chain first, so a patient with many chunks starts early instead of finishing last. A local engine, which batches prompts itself, uses rounds.
    • rounds: the first chunk of every patient is sent as one batch, then every second chunk, and so on, so each round waits for its slowest patient.

    Prompts are built in patient.prompt_build_workers processes under both. The two give the same prompts, quality checks, retries and results, and either can resume the other's checkpoint_dir, including round files from runs before the chunk journal (see Resuming patient summarization). Under an endpoint pool, rounds also reports its first round's per-request endpoints in model_metadata["responses"]; continuous reports where each request ran only in the debug attempt traces.

    patient.local¶

    Local in-process vLLM runtime settings. See trial.local. The patient context (engine.max_model_len, 200,000 tokens) also bounds remote requests: each one's output budget (max_tokens, 50,000) is reduced to what fits after its prompt.

    patient.prompt_files¶

    Prompt template filenames loaded from matchminer_ai.prompts.

    patient.reasoning_parser¶

    vLLM reasoning parser name. The default auto resolves known model names, including the default nvidia/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B-NVFP4 to nemotron_v3 and google/gemma-4-31B-it to gemma4. Set this explicitly when using a model not covered by the package mapping, or use none to disable reasoning parsing for a non-reasoning model. Non-vLLM remote endpoints may return no separate reasoning field.

    patient.remote¶

    Task-specific remote chat completion request settings. See trial.remote. Patient summarization also supports tokenizer_name, which is the local tokenizer used for patient chunk truncation and prompt sizing before sending requests to the remote endpoint. For self-hosted vLLM this is usually the same as patient.remote.model_name.

    patient.text_token_threshold¶

    Maximum token count used by local truncation before patient summarization.

    document_extraction¶

    Configuration for patients.extract_document_records, which extracts one structured record per note (see Structured Clinical Extraction). Its local, remote, sampling_profile, reasoning_effort and reasoning_parser fields follow the other LLM task sections; the default model is Nemotron 3.5 Super with its own sampling (sampling_profile: auto).

    • max_document_characters (default 200,000): longer notes fail rather than being truncated.
    • max_attempts (1-10, default 3): attempts per note for an answer that fails validation, including a quote that is not in the note. With reasoning_off_fallback (default true) one more attempt runs with thinking off. After the last attempt, items left without any quote found in the note are dropped and the record is partial; any other problem fails the note.
    • structured_outputs (default true): with the remote backend, each request carries the record's strict JSON schema as response_format (vLLM structured outputs).
    • batch_size (default 256) and batches_in_flight (default 2, at most 16): a local backend gets batches of batch_size, batches_in_flight at once. A remote backend keeps as many requests in flight as its servers take, remote.max_concurrent_requests for each listed server, each sent as another returns, so that cap alone sets a run's concurrency; it is never fewer than batch_size * batches_in_flight, which also applies to servers from a registry file (remote.server_urls_file, whose own ceilings then limit each server).
    • extensions (default []): disease-specific item types and guidance by name; the package provides thoracic.
    • ncit_agent_codes (default false): add each treatment agent's NCIt concept from the bundled NCIt snapshot (ncit_resource, by default good_option_catalog.ncit_resource).

    The default completion budget is 50,000 tokens, reasoning included (Nemotron often reasons for 10,000-15,000 tokens before an answer whose quotes add more; one synthetic molecular report took 29,867), in a 131,072-token local context. A remote completion of that length can take far longer than the default remote.request_timeout of 600 seconds on a busy server; raise it (for example to 7,200 seconds), since the endpoint pool retries timed-out requests from the start.

    patient_extraction¶

    Configuration for patients.extract_patient_records, which builds one record per patient from all of their notes. It takes the document_extraction keys above except max_document_characters, plus:

    • chunk_tokens (default 40,000) and chunk_overlap_tokens (default 500): notes are packed in date order into chunks of at most chunk_tokens tokens of the model's tokenizer (remote.tokenizer_name, or the model name); a longer note is split at token boundaries with that overlap.
    • context_tokens (default null, meaning local.engine.max_model_len): a chunk's prompt, including the record so far, plus the completion budget must fit; a patient whose next prompt would not fit fails rather than being truncated.

    The default local batch is 64 requests, the completion budget 60,000 tokens and the local context 200,000 tokens. A remote backend keeps remote.max_concurrent_requests requests per server in flight, as for document_extraction; each patient's chunks still run one after another.

    workup_sql_agent¶

    Configuration for patients.compile_workup_sql (see SQL-Agent Workup Checks). For each distinct workup requirement, an LLM agent explores an extraction database with read-only SQL in an isolated worker and accepts one cohort-level query. It needs an OpenAI-compatible endpoint (remote.enabled; a local vLLM server works), not an in-process engine. Exploration results are patient-derived extracted values (no ids, note text or quotes) and reach that endpoint.

    Top-level keys: - max_attempts (3): attempts per turn for an invalid action. - structured_outputs (true): JSON-schema responses; false sends the schema in the prompt only. - tokenizer_mode (bytes): conservative local prompt budgets; endpoint counts with /tokenize. - context_window (null): null uses local.engine.max_model_len, then the endpoint's /v1/models. - request_timeout (600): seconds a turn's request may go without data before it is retried, instead of the shared remote.request_timeout. A 429 or 503 is waited out (from 10 s, at most 60 s) within max_attempts. - sampling_profile, reasoning_effort (high) and reasoning_parser, as for other LLM sections. - local / remote: the model, with 32,000 completion tokens per turn by default.

    limits keys: - max_actions (12) and max_submits (3). - submit_by (6): the action by which the agent is asked to submit a first candidate. - max_review_queries (3): checking queries allowed after a valid submission. Then code removes the query action, and the agent accepts the submission or submits a revision. - max_rows (30), max_cell_chars (160) and max_result_chars (6,000): what the agent sees of a result. - max_memory_chars (4,000), max_recent_steps (8), max_sql_chars (16,000). - max_search_terms (8) and max_search_rows (50): words per search, and matching text values a search shows. - max_detail_chars (300) and max_evidence_items (8): per-patient output. - sample_rows_per_status (3): example rows shown after a submission. - max_concurrent_items (8): requirements explored at once, sharing one worker. Each turn is one request, so the agent's request cap is raised to at least this. - query_timeout_seconds (20) and final_timeout_seconds (120). - worker_memory_mb (4,096) and duckdb_memory_mb (2,048).

    trial_space_criteria_extraction¶

    Configuration for extracting the complete inclusion and exclusion criteria relevant to one trial space from a UTF-8 OCR text file. Its local, remote, and reasoning_parser fields select the same LLM backend pattern as other tasks.

    • max_document_characters: hard input bound. Oversized documents fail rather than being silently truncated and losing criteria.
    • max_criteria_per_type: maximum number of inclusion criteria and maximum number of exclusion criteria accepted from the model.
    • response_retry_limit: retry bound for malformed JSON, invalid schemas, duplicate criteria, and criteria that are not grounded in the OCR text.

    The default extraction task keeps model thinking enabled and allows up to 50,000 completion tokens. The default remote request uses JSON-object response formatting. The entire OCR document and trial space reach the configured LLM backend; no web search is used. Every accepted criterion must match a source excerpt after conservative whitespace, ordinal-suffix, repeated page-edge, and referenced trailing-footnote normalization.

    protocol_cohort_extraction¶

    Configuration for extract_protocol_cohorts, which screens full protocol documents (PDF, OCR text or Markdown) and extracts their cohort eligibility criteria. Its local, remote, sampling_profile, reasoning_effort and reasoning_parser fields follow the other LLM task sections.

    • max_document_characters: hard input bound (default 800,000 characters). Oversized documents fail rather than being truncated.
    • max_attempts: validation attempts per request (1-10, default 3); only failed requests are retried, and a cohort that fails every attempt fails its protocol.
    • chunk_size (default 500) and chunks_in_flight (default 2, at most 16): a remote backend keeps chunk_size * chunks_in_flight requests in flight, each sent as another returns; a local backend gets batches of chunk_size requests of one step, chunks_in_flight at once. With output_dir, each protocol is saved as soon as it is decided.
    • structured_outputs: when true and the remote backend is enabled, each request carries a strict JSON-schema response_format for its step.
    • prompt_files (optional): maps screen, list and criteria to other packaged prompt files; by default protocols use the same three prompts as ctgov listings (trial.cohorts.screen.user.txt, trial.cohorts.list.user.txt, trial.cohorts.criteria.user.txt).

    The default model context is 262,144 tokens with up to 50,000 completion tokens, so that full industry protocols (often 50,000-160,000 tokens) fit with room for reasoning.

    synthetic_protocol_generation¶

    Configuration for generate_synthetic_protocols. Its local, remote, sampling_profile, reasoning_effort and reasoning_parser fields follow the other LLM task sections.

    • chunk_size (default 500) and chunks_in_flight (default 2, at most 16): a remote backend keeps chunk_size * chunks_in_flight requests in flight, each sent as another returns, so one slow protocol holds up only itself; a local backend gets batches of chunk_size, chunks_in_flight at once. Outputs are written when their request returns.
    • max_attempts: attempts per trial for empty or truncated outputs (1-10, default 3).
    • layouts_file: optional override of synthetic_protocol_layouts.json.

    The default model context is 262,144 tokens with up to 100,000 completion tokens, so long protocols and reasoning traces fit.

    embedding¶

    Configuration for TrialSpace embedding. Retrieval embeds key text only: patient key sections (cancer_history_summary) and cohort key criteria (cohort_key_criteria); see the embedding API.

    The section maps onto the training repository's encoder settings (matchminer_ai.embedding.encoder.EncoderSettings), and embed_for_matching loads and encodes with the same functions training's mining uses, so the default encodes exactly as training encoded its model.

    embedding.model_path¶

    Sentence-transformer model path or Hub id passed to SentenceTransformer(...).

    The default is a local, unpublished directory, on purpose (user, 2026-11-12): the n=5000 run's round-2 TrialSpace, /ksg/kehl_mm_data/mmai/v23/data/no_phi/synthetic_dataset_n5000_screened_20261106/trialspace/models/trialspace_round2 (google/embeddinggemma-2 fine-tuned by finetune_embedder.py). A path that starts with / or ., or that exists, must be a readable directory; otherwise embedding (and embedding token counts) fail with FileNotFoundError, so runs on a machine without that directory stop instead of mixing vectors. Nothing falls back to ksg-dfci/TrialSpace-0526 or any Hub model. The model was saved by sentence-transformers 6.1 and needs 6.1 or later to load.

    embedding.device¶

    Device string passed to SentenceTransformer(...). Autocast applies on CUDA only, so CPU vectors (float32 throughout) are not interchangeable with CUDA vectors; the encoder identity stored with cached vectors records which was used.

    embedding.dtype, embedding.autocast¶

    Weight precision (float32 or bfloat16) and CUDA autocast precision (bfloat16). The defaults, float32 and bfloat16, are training's mining settings. Absent, the model's own dtype is kept and autocast is off.

    embedding.prompt_profile, embedding.default_prompt_name¶

    prompt_profile: trialspace applies trialspace_contract.model_prompts("trialspace") over the model's saved prompts, as mining does: patients are encoded with patient_summary and cohorts with this_space. A TrialSpace trained by matchminer-ai-training saves the same prompts. default_prompt_name (SentenceSimilarity) is the prompt for calls that name none. Absent, the model's saved prompts are used unchanged.

    embedding.include_prompt_in_pooling, embedding.text_only¶

    Mean pooling over the prompt tokens as well as the text (true, as trained), and loading EmbeddingGemma 2 without its vision and audio towers (true). These settings are specific to EmbeddingGemma 2 TrialSpace models; remove them when pointing model_path at another model family.

    embedding.batch_size¶

    Texts per encoder batch (default 32, as mining encodes; 12 when absent).

    On CUDA, embedding first uses PyTorch's default scaled-dot-product-attention dispatcher. If cuDNN reports that it cannot build a valid attention execution plan, the package retries with the CUDA flash, memory-efficient, or math attention backends and remembers that fallback for the same model and device. Other runtime errors are not retried.

    embedding.prompt_file¶

    Prompt filename loaded from matchminer_ai.prompts and used as the query prompt only for a model that saved none and has no prompt_profile (so never for the default); a model's saved prompts are never replaced. The file is prepended exactly as written (only its final newline is removed). The default, embedding.txt, is byte-identical to TrialSpace-0526's saved query prompt, including its trailing space. A TrialSpace model that saves prompts named patient_summary and this_space encodes each side with its own prompt.

    embedding.max_seq_length¶

    Runtime truncation cutoff for embedding inputs (default 4096, the round-2 fit's cap; the n=5000 round-3 mining encoded at 8,192, which changed one synthetic cohort in 15,263). SentenceTransformer uses this value during encode(), so inputs longer than this limit are truncated before embedding generation. QC reports use the same value, counting tokens with each side's prompt, when flagging key text that exceeds the embedding input limit.

    This value should match the model_path configured alongside it — it is specific to the embedding model in use, not a general-purpose default. Changing embedding.model_path to a different model without reviewing max_seq_length against that model's own native truncation cutoff (e.g. its sentence_bert_config.json) can silently truncate inputs at the wrong point, producing different embeddings than the model would otherwise produce for longer inputs.

    decision_model¶

    decision_model.model_name¶

    decision_model.revision¶

    The commit of a Hub model (default 652f920e544ea37f81e4b0ce89b81d4ed0da90b1, d1-2B's main on 2026-11-05). Required for every Hub model, because its code runs; ignored for a local directory.

    decision_model.backend¶

    transformers (the only backend).

    decision_model.device / decision_model.dtype¶

    Where the model runs (default cuda) and its weight type (default bfloat16).

    decision_model.max_length¶

    The fine-tuning request length (default 10000 tokens). Longer requests still run, without truncation, and are counted in the metadata's over_max_length.

    decision_model.set_size¶

    decision_model.token_budget / decision_model.batch_size¶

    decision_model.compile¶

    llm_good_option¶

    Configuration for experimental-drug selection during patient-free research and for the patient-specific four-point-per-drug LLM scorer. Its local and remote blocks follow the same structure as trial.local and trial.remote. The default request enables model thinking, permits up to 100,000 completion tokens within a 262,144-token local context, and uses a repetition penalty of 1.1. Each scoring message describes exactly one patient; the backend may batch many independent messages in one run. score_good_options_with_llm can selectively retry code-validation failures with max_parse_attempts; each follow-up includes the prior invalid answer, exact parser error, and finish reason. Set reasoning_off_fallback=True to add one final attempt with thinking disabled after the ordinary attempts are exhausted.

    good_option_catalog¶

    Configuration for patient-free trial drug extraction, evidence synthesis, and clean task-specific projections. synthesis_evidence_max_tokens bounds the raw evidence packed for one drug, and it bounds passage text only: the JSON scaffolding around the passages adds roughly 6.5%, so the real prompt costs about 1.08x this value. It defaults to 190,000, which pairs with the 262,144 max_model_len of the local synthesis engine and leaves roughly 50,000 tokens for a reasoning trace and the final JSON. Evidence beyond the budget is discarded round-robin across sources before the model sees it, so a lower value silently drops passages rather than failing; when serving a smaller context, reduce it to about (context - completion budget) / 1.08. Synthesis reads the ledger in synthesis_chunk_max_tokens chunks (default 60,000; classes use class_evidence_max_tokens). Each chunk's call sees the facts so far and returns only new or revised items, which code merges in: an existing fact is removed only when a validated item names it in replaces. The stage-specific synthesis_llm override defaults to a 100,000-token completion budget so reasoning-enabled models can think over a chunk and still finish the final JSON. Larger chunks are not better: on 40 multi-chunk drugs with Gemma 4 31B, 100,000-token chunks gave about 25% fewer facts and cited passages than 60,000, because the model condenses more of each chunk. A chunk plus passage metadata, the existing facts (up to about 25,000 tokens for the broadest classes), and this budget must fit together in the served context; lower both chunk limits when serving less than 262,144 tokens, since the endpoint rejects a request whose prompt plus max_tokens exceeds its context. A model that exhausts the budget mid-trace returns an empty answer with finish_reason=length, which is retried rather than silently accepted, and if every ordinary attempt ends that way the final attempt disables thinking. screening_max_attempts and synthesis_max_attempts control structured-output retries. screening_checkpoint_batch_size and class_checkpoint_batch_size (default 64 each) are how many trials are screened, and drugs classified, at once. With a remote backend each trial or drug is its own request and retries, validated and checkpointed as soon as it finishes, and the next waiting one starts in its place, so one slow answer holds one slot instead of a batch; the endpoint pool still caps each server's concurrent requests, and units beyond that wait for it. A local engine, which batches prompts itself and is not thread-safe, gets groups of these sizes instead, checkpointed when each group returns. Either way each trial or drug gets its own prompts, retries and checkpoint, recorded in input order, so the sizes only schedule. Both keys are still part of the checkpoint fingerprint, as they always were, so changing them here starts a new checkpoint directory; the command line's --llm-batch-size overrides both for one run without entering the fingerprint, so a build can resume with another value. Synthesis is not batched either: each drug or class is its own chain of chunk calls, checkpointed as soon as that chain finishes, with up to remote.max_concurrent_requests chains in flight. Screening and synthesis LLM overrides inherit from llm_good_option. With a remote backend, structured_outputs (default true) decodes the screening and class answers under their JSON schemas (response_format json_schema); set it to false for a server without that support, and the answers are parsed and validated from free text as before.

    Evidence is also retrieved on two axes beside the drug's own name, and each has its own budget so that neither can evict the other.

    The classify stage gives an NCIt-matched drug every NCIt class above its concept, below the fixed umbrella concepts, without an LLM call; those are not capped. class_max_per_drug (default 3) caps the classes the LLM may add on top, or name for a drug NCIt leaves unclassified; an added NCIt class's own ancestors do not count against it. class_candidate_limit (default 25) bounds the NCIt candidate classes, found by local search of class names and synonyms in the drug's name, definition, and mechanism passages, that the LLM may choose from by code. class_assignment_evidence_max_tokens (40,000) bounds the mechanism passages that stage reads and searches, and class_llm gives it its own completion budget. class_evidence_max_tokens (60,000) bounds each chunk of the corpus that class synthesis reads. Class synthesis is a separate call from agent synthesis rather than a larger pooled one: 165 drugs already use more than half the agent budget and the largest uses 91% of it, so pooling would let a flood of same-class passages evict the agent's own data. class_option_summary_max_tokens bounds each class's stored projection. The scoring prompt re-renders classes and drugs from their structured facts instead, under good_option_prompt.

    Retrieval settings for both axes live on ResearchSettings rather than in this block: class_facets, class_sources, class_research_rounds, and the max_class_* record caps for the class axis, and indication_terms_per_drug (default 25), indication_facets, indication_sources, and the max_indication_* caps for the indication axis. Indication terms come from the conditionsModule.conditions of the trials a drug appears in, falling back to derivedSection.conditionBrowseModule.meshes, so the catalog stays patient-free and cacheable. Both axes call only the query-driven sources; the ctgov, label, and curation adapters search by exact agent name and return nothing for a class name.

    indication_facets defaults to efficacy_by_tumor, biomarker_prevalence, and biomarker_directed_efficacy for both drug–disease and class–disease retrieval.

    Research requests are paced per host, in one budget shared by every subject researched at once and by every stage, the ctgov record fetch included; retries and redirects count against it. Requests to a host take turns, each a full interval after the previous one actually left, over a connection pool of the host's own, so neither a busy event loop nor page downloads to other hosts can release them in bursts. The defaults keep each service about 30% under its per-IP ceiling:

    Host Requests per second Ceiling
    clinicaltrials.gov 0.6 (36 a minute) none published; about 50 a minute per IP is the commonly reported limit
    dailymed.nlm.nih.gov 1.0 none published; its 429s carry Retry-After: 60
    eutils.ncbi.nlm.nih.gov 2.0, or 7.0 with an NCBI API key 3 a second per IP without a key, 10 with one

    The 2026-11-12 catalog rerun paced only E-utilities, at 2.5 a second in the client's shared connection pool. A quarter of its ClinicalTrials.gov requests came back 429, in research and in the serial record fetch (about 74 a minute), as did 8% of its saved PubMed attempts and 4% of DailyMed's. Europe PMC, CIViC and cancer.gov returned none and stay unpaced; general-web searches are bounded by --web-search-concurrency instead.

    • host_requests_per_second (default {}): per-host overrides of these defaults, for example {eutils.ncbi.nlm.nih.gov: 1.5}; 0 leaves a host unpaced. The command line's --host-requests-per-second HOST=RATE overrides it. A limit is per IP, so two builds on one machine should split it.
    • ncbi_api_key_file (default null): a file holding an NCBI API key, sent with PubMed's E-utilities requests and raising their default rate to 7 a second. --ncbi-api-key-file overrides it, and either overrides the NCBI_API_KEY environment variable, which is read when neither is set. The key travels only in request bodies, never in a URL, log line, error message, research attempt, checkpoint or manifest.

    Both keys only schedule requests, so they are left out of the checkpoint fingerprint: an existing checkpoint directory resumes with new rates, or with a key added or removed.

    good_option_prompt¶

    Patient-time packing of catalog drug and class evidence into the llm_good_option prompt. It lives outside llm_good_option and good_option_catalog because those sections fingerprint catalog checkpoints.

    • context_tokens (default null): the teacher's context window. null uses llm_good_option.local.engine.max_model_len (262,144); set it when a remote endpoint serves a different length.
    • chars_per_token (3.5): conversion rate for the budget. Conservative for Gemma 4, which averages about 4.4 characters per token on catalog text, and for Nemotron 3.5 Super, whose tokenizer averages the same as Gemma 4's (4.6) on ctgov eligibility criteria.
    • safety_tokens (4,096): margin kept beyond the completion allowance, which is the active backend's llm_good_option max_tokens.
    • max_drug_section_tokens, max_class_section_tokens (20,000 each): upper bound on any one drug or class, however much room remains; null removes it.

    See Evidence packing for how the budget is shared and when evidence is condensed.

    good_option_check¶

    Settings for check_good_options, the on-demand patient-trial check. They are applied to a copy of the config at call time and stay outside llm_good_option so catalog-build fingerprints are unaffected.

    • max_output_tokens (50,000): completion cap for the scoring request, replacing the active backend's llm_good_option max_tokens (100,000) so more of the context carries evidence. null keeps the llm_good_option value.
    • discover_context_tokens (true): when good_option_prompt.context_tokens is unset and remote inference is enabled with an OpenAI-compatible provider, size evidence packing to the smallest max_model_len the servers report at /v1/models.
    • discovery_timeout_seconds (10.0): timeout for each lookup. A failed lookup falls back to the configured context and is reported in the metadata.
    • max_parse_attempts (3): total attempts for answers that fail validation.
    • reasoning_off_fallback (true): add one final attempt with thinking disabled.
